Merge, squash or rebase

GitHub's three pull request buttons all put the same code on main. What differs is the history you're left with.

Which to pick

  • Default to squash and merge. One commit per PR keeps main easy to read and each change easy to revert.
  • Use a merge commit for release or long-running branches, where the separate commits are worth keeping.
  • Use rebase and merge only when the author has already shaped the commits for review.

After a squash or rebase, git branch -d refuses

Git reports that the branch is not fully merged, because main now holds new commits, not the branch's own. Check that the PR shows as merged, then delete the branch with git branch -D parser.

Button names are GitHub's. Azure DevOps offers the same three as "Merge (no fast forward)", "Squash commit" and "Rebase and fast-forward", plus a fourth, "Semi-linear merge".
